# UX audit — 2026-09-25 (Phase 12, UX polish)

Scope: fixes only. Every suggestion below changes existing behaviour, copy or layout. Anything that would add a
feature is listed under [Out of scope](#out-of-scope-rejected-ideas).

## Method

- Production build (`next build` + `next start` on a local port, `.env.test`, local Postgres container) with the
  E2E mock AI servers. A second instance with no AI keys was used for the "not set up" state.
- Seeded fixtures: an owner with an upcoming event (5 RSVPs, one very long guest name, long title and location), an
  event with no RSVPs, a past event, an organizer with no events, a user with the cleared-password notice pending, and
  the demo event.
- Automated sweep with Playwright: 19 screens × 3 widths (375, 768, 1280) × 2 themes × 3 locales (en, fr, pt-BR) =
  342 page loads, full-page screenshots, horizontal-overflow check, target-size check (all visible controls, 24×24 px
  minimum), clipped-text check, and axe-core (WCAG 2.0/2.1/2.2 A+AA rules) at 375 and 1280 in both themes.
- Scripted journeys, mostly at 375 px with touch emulation: sign-in and register errors, guest RSVP (Going, Not going,
  change, cancel, duplicate name, over-limit party size), ended event, owner tools (copy link, remove RSVP, delete
  event), event form (empty submit, past date, AI empty text, AI success, AI failure, AI not set up), account
  (mismatch, wrong current password), user menu, locale switcher, theme toggle.
- Keyboard-only checks: tab order on home and the guest page, focus after every async action and inline confirm,
  Escape behaviour, arrow keys on the radio group and the language select.
- Screenshots are kept in the auditor's temp directory (`<tmp>/shots/`); file names are quoted in the table as
  evidence.

Reference: Nielsen's 10 heuristics (N1–N10), WCAG 2.2 AA, `docs/DESIGN.md`, `docs/PRODUCT.md`.

## Summary

| Severity | Count |
|---|---|
| High | 4 |
| Medium | 11 |
| Low | 12 |
| **Total** | **27** |

No horizontal scroll at any width or locale, no control under 24×24 px, and no axe colour-contrast violation in either
theme. The problems are behavioural: focus management, state carried across edits, page titles, and a few dead ends
and vague messages. These are the same kind of issue as the two the external reviewer found.

## Top 10

1. **UX-01**: switching from Not going to Going leaves the party size at 0 and the RSVP fails.
2. **UX-04**: focus is lost to `<body>` on every async submit (disabled loading button).
3. **UX-02**: no `<title>` on any page (WCAG 2.4.2, A); also affects invite-link previews.
4. **UX-03**: the language select navigates on the first arrow key (WCAG 3.2.2, A).
5. **UX-05**: validation errors show off screen at 375 px and focus does not move to them; alerts repeat four times.
6. **UX-06**: RSVP confirmation is not reliably announced and focus is lost after Send, Change and Cancel.
7. **UX-07**: no way to back out of "Change" without resubmitting.
8. **UX-08**: AI fill with empty text says "fix the highlighted fields" and nothing is highlighted.
9. **UX-10**: unknown URLs show Next's unstyled English 404 (no header, no `lang`, white in dark theme).
10. **UX-11**: the invite link field shows only "http…" on phones in French and Portuguese.

## Forgot-password hint

Place it **under the Password field on the sign-in page**, as the field's hint (`FieldHint`, `id="signin-password-hint"`,
referenced by the password input's `aria-describedby`). It is always visible, not only after a failed attempt.
Keep it out of the error alert: a user who knows they forgot the password should not have to fail first. It sits
just below the Google button, so "above" is literal at every width.

| Locale | Key `auth.forgotPasswordHint` |
|---|---|
| en | Forgot your password? If your email is a Google account, use Continue with Google above, then set a new password in Account. |
| fr | Mot de passe oublié ? Si votre e-mail est un compte Google, utilisez « Continuer avec Google » ci-dessus, puis définissez un nouveau mot de passe dans Compte. |
| pt-BR | Esqueceu a senha? Se o seu e-mail é uma conta Google, use "Continuar com o Google" acima e depois defina uma nova senha em Conta. |

The button names must match the live `auth.continueWithGoogle` and the menu label `nav.account` in each catalog.
The wording points only to existing flows: Google sign-in on the same email (which clears the old password and shows
the existing cleared-password notice), then Account → Set a password. It promises no email reset. "If your email is a
Google account" keeps it honest for addresses that cannot use Google sign-in.

## Would a mobile Playwright project have caught these?

Only partly. A `Pixel 7` or `iPhone 13` project **running the existing specs unchanged** would catch none of the
findings. The specs assert behaviour, not viewport-dependent layout, and they already pass at 375 px.

- **Caught by a mobile project plus viewport assertions** (`toBeInViewport`, element width, no mid-token wrap):
  UX-05 (first error above the fold only at 375), UX-11 (invite field 67–132 px wide), UX-15 (offset wraps only at
  375/en). UX-22 is more visible on phones but is not width-dependent.
- **Not width-dependent; missed because no journey covers them:** UX-01 (Not going → Going), UX-07, UX-08,
  UX-14, UX-21, UX-24. A journey test would catch UX-01 on any project.
- **Not caught by any project without focus or semantics assertions:** UX-02 (would be caught by the axe rules the
  sweep used, in a single desktop run), UX-03 (Windows Chrome/Edge keyboard behaviour; a mobile project uses a
  touch picker and would never see it), UX-04, UX-06, UX-09.

Recommendation: adding a mobile project is cheap, but most of the value comes from three assertions added to the
existing specs, whichever project runs them:

1. After a failed submit, focus is on a field or an alert, not `<body>`.
2. axe `document-title` and `html-has-lang` pass on every page.
3. The Not going → Going journey sends successfully.

## What works well

- No horizontal scroll, clipped control label or target under 24×24 px at 375/768/1280 in all three locales. French
  strings fit everywhere except the invite field (UX-11).
- Both themes pass axe colour contrast on every audited screen. The theme is applied server-side with no flash.
  Status pills pair icon and word, never colour alone.
- Inline confirms (Delete event, Remove) move focus to "Keep", close on Escape and return focus to the trigger.
- The Going / Not going radio group works with arrow keys, shows a visible 2 px ring, and hides the stepper for
  Not going.
- The owner's guest list turns into readable stacked rows on phones. A 50-character guest name wraps cleanly
  without pushing the Remove button off screen.
- Copy invite link gives a visible "Copied" state and a polite live announcement, and copies the right URL.
- Error copy for duplicate names, rate limits, wrong credentials and each AI failure cause is specific and says what
  to do next.
- The empty dashboard explains the three steps and offers the sample event. The cleared-password notice is clear
  and dismissible.
- Guest tab order on the event page is short and logical: header, Add to calendar, name, answer, party size, send.

## Out of scope (rejected ideas)

Considered and rejected because each adds a feature rather than fixing existing behaviour:

- Email-based password reset or magic link (UX-13 points to the existing Google path instead).
- Open Graph image or rich invite-link preview cards (UX-02 fixes only the missing title/description).
- Show/hide password toggle.
- Undo for Remove RSVP or Delete event.
- Sorting, filtering or exporting the guest list.
- Custom (non-native) date, time or timezone pickers; searchable timezone combobox.
- Toast or snackbar system for confirmations.
- Web Share API "Share" button next to Copy link.
- Skip-to-content link: header has four stops and `<main>` is a landmark, so WCAG 2.4.1 is met without it.
- Live (as-you-type) validation.
- Relaxing the RSVP rate limit for guests on a shared IP (policy change, not UX polish; noted during testing when
  10 submissions in 10 minutes blocked further changes).
